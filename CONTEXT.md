# MSI Forge — Domain Context

## Glossary

- **MSI Forge** — The unified AI platform combining code intelligence (Analyst) and test automation (Test). BAs use Analyst modules to reverse-engineer code into Knowledge Bases and generate Requirements Documents. Developers use Test modules to generate and execute Playwright tests grounded in that code intelligence.
- **Workspace** — Top-level organizational container. Owns all projects, AI provider config, and integrations. Single workspace per user for MVP.
- **Project** — A client engagement. Has an optional app URL (for testing) and an optional GitHub repo URL (for code analysis). A project can be Analyst-only, Test-only, or both. Belongs to a workspace.
- **Knowledge Base** — A structured, indexed representation of a project's codebase stored in Convex. Contains architecture summary, module map, code chunk embeddings, API surface, data models, and user flows. Built during onboarding via the ingestion pipeline, refreshed on demand.
- **Baseline RD** — A Requirements Document generated by AI from the production codebase. The authoritative description of what the app currently does. Editable by BAs. Versioned — each re-sync increments the version.
- **Old RD** — An existing Requirements Document uploaded by the BA. Serves as format reference and business context for drift detection, not source of truth. May be stale.
- **Drift Report** — A comparison between the Old RD and the current codebase. Lists features added, removed, or changed since the Old RD was written. Generated only when an Old RD is available.
- **Code Chunk** — A segment of source code stored in the Knowledge Base with a vector embedding for semantic search. Chunked by file or logical section, grouped by module.
- **Module** — A major feature area or domain boundary detected in the codebase by AI during Knowledge Base construction. Contains related APIs, data models, and user flows.
- **Feature Request** — A client requirement pasted into the chat for analysis. The AI analyzes it against the Knowledge Base to produce an Impact Analysis and User Stories.
- **Impact Analysis** — A structured breakdown of which modules, APIs, data models, and user flows are affected by a Feature Request.
- **User Story** — A structured requirement generated by AI with title, description (As a... I want... So that...), acceptance criteria (numbered, testable), and affected system components. Stored as structured artifacts, not just chat text.
- **Thread** — A chat conversation. BA chat threads are scoped per project, managed by the Agent Component. Test generation threads are scoped per suite (derived ID).
- **Suite** — A named group of tests within a project. Auto-created per generation action with a descriptive default name.
- **Test** — A single test scenario. Stored in either Playwright TypeScript code (`playwright_code`, execution_type `"playwright"`) or hybrid NL+code steps (`steps` array, execution_type `"stagehand"`). Has a source type (url_exploration, prd, natural_language) and status (draft, approved, healing).
- **Run** — An execution of one or more tests. Can be a suite run, single-test run, test-list run, or rerun. Tracks trigger type (manual, ci, scheduled, rerun), environment, overall status, runner_id, and last_heartbeat_at (liveness signal). A Run stuck in running status without a recent heartbeat is marked failed.
- **Step** — A single action within a test execution. Records the command, locator, pass/fail/skipped status, screenshot, and timing.
- **Runner** — The separate Node.js process that executes Playwright tests outside Convex. Stateless execution engine; Convex is the source of truth for all state.
- **Exploration** — The guided flow where the system navigates a target app URL. The Runner renders pages with Playwright, takes DOM snapshots and screenshots, and sends structure to Convex where the AI proposes testable scenarios.
- **Stagehand** — An AI-powered browser automation library by Browserbase, built on Playwright. Used for smart exploration and execution of hybrid NL+code tests.
- **Auto-Heal** — The system's ability to automatically repair failing tests. When a test fails, the AI analyzes the error and current page state to produce a corrected version. Healing confidence threshold determines auto-accept vs. human review.
- **AI Insight** — An AI-generated analysis linked to a test failure. Contains root cause text, suggested fix, and confidence score.
- **Flakiness** — A measure of test instability across multiple runs. Computed as the ratio of inconsistent results over recent run history.
- **Environment** — A named deployment target (e.g. staging, production) with a base URL, scoped to a project.
- **AI Agent** — A specialized `@convex-dev/agent` instance with a defined role, system prompt, and tools. MSI Forge defines seven: Test Generation Agent, Hybrid Test Generation Agent, Exploration Analysis Agent, Failure Analysis Agent, Test Healing Agent, Test Refinement Agent, and Analyst Chat Agent.
- **Agent Tool** — A Convex query that an AI agent can invoke during generation to fetch context from the database. Seven tools are defined: `readExistingTests`, `readProjectContext`, `readTestCode`, `readPreviousExplorations` (stub), `readRecentFailures` (stub), `readKnowledgeBase` (Analyst), `readBaselineRd` (Analyst).
- **AI Error** — A structured error from AI operations. Uses `ConvexError` with `{ type: "ai_error", code, message }` where code is one of: `invalid_api_key`, `rate_limit`, `timeout`, `malformed_response`.
- **Constraint** — A shared validation rule (e.g., name length 1-100, password min 8) defined once in `convex/lib/constraints.ts` and consumed by both frontend zod schemas and backend Convex validators.
- **Owned Entity** — Any database document scoped to a workspace. The ownership check (`entity.workspace_id === workspace._id`) is centralized in `getOptionalOwnedEntity`.
- **Context-Aware Test Generation** — The integration bridge between Analyst and Test modules. When a project has a Knowledge Base, test generation queries it for module structure, API surface, and user flows — producing more accurate tests than PRD text alone.

## Data Hierarchy

```
Workspace → Project ─┬─→ Knowledge Base → KB Module → (APIs, Data Models, User Flows)
                     ├─→ Baseline RD (versioned)
                     ├─→ User Stories (from chat threads)
                     ├─→ Suite → Test → Run → Step
                     ├─→ Exploration
                     └─→ Environment

Workspace → Schedule → Run (scheduled runs)
Workspace → Test List → Test (cross-project grouping, pointers only)
```
